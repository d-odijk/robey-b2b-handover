Design history (archive)

Full record of the design process with dates and rejected alternatives. Not needed to build; see HANDOVER.md for the current state.

This document describes the design of the new Robey B2B dealer portal in such a way that it can be built: which files apply, which values are fixed, how components behave, and which questions are still open. It is written to be fed to Claude Code together with the source files.

What this is, and what it is not

The source files are design code: HTML with inline styles, made to show exactly how something looks and feels. It is not production code and must not be copied.

What can be taken over literally:

  • All values: colours, spacing, radii, shadows, font sizes, hover behaviour. These are not estimates from an image but the real CSS.
  • The structure of each component (which elements, in which order, with which role).
  • The behaviour: smart header, hover panels, the stock/preorder toggle, the cart model.
  • The texts. They have been thought through and agreed; they do not need to be written again.

What not: inline styles, the absence of components, base64 images, the absence of responsive behaviour and data binding. The stack (headless on Shopify Plus with B2B) calls for components with props and data from the Storefront and Customer Account APIs.

Files

There are three canvases, because the editor loads at most 200 files per canvas: Robey B2B schermen (desktop · 1200+, plus the sketches and proposals), Robey B2B mobiel en tablet (pages Tablet liggend · 900–1199, Tablet staand · 768–899, Mobiel · &lt; 768; separate since 14 September) and Robey B2B archief (older versions). Seeding is done with python3 seed.py canvas.json robey-b2b-schermen.html "Robey B2B schermen", python3 seed.py canvas-mt.json robey-b2b-mobiel-tablet.html "Robey B2B mobiel en tablet" and python3 seed.py canvas-archief.json robey-b2b-archief.html "Robey B2B archief" (only the images the artboards use are included).

What is really a different component

Not everything that looks different is also different work. Three categories:

One component, different grid. Product tile, collection tiles, personal blocks on the homepage, account lists, Downloads, Klantenservice, Retourneren. Same structure, only the number of columns changes. One responsive implementation is enough here; the artboards show the same parts.

One component, different placement. Cost summary (amounts and totals side by side on desktop, two columns on tablet, stacked on mobile), switch link, PDP gallery, search field. Same content and same data, different layout. One component with two layouts.

Really two components. The size matrix and the cart card. Below 768 the matrix is not a narrower grid but a card per colour that you expand, with size chips and three cells per row; that is a deliberate choice, not a lack of space. Twelve sizes side by side does not work at 390 and an expander does not work at 1440. Count on two implementations here that share the same state. The same goes for the header: the mobile header with overlay is something different from the smart sticky header.

What is not yet fixed

  • 1024 to 1199 is drawn as tablet landscape, but on a 1280 laptop you are already in the desktop design. The transition at 1200 has not been tested on a real screen.
  • Above 1400 the page does not stretch further: everything sits in a wrap of max 1320 with 40px side space (content 1240). That is deliberate. On 19 September the wrap was briefly 1400 for the product page according to sketch D; Dennis found the narrower width more pleasant to scan for the menu and other pages, so the wrap is back to 1320 and the matrix row on the product page has been made more compact (colour column 140, totals column 150, gap 32) so that D fits with a photo of 369 px. The current B2B has a fixed container of about 1380.
  • There is no artboard between 900 and 1199 for Downloads, Retourneren and Klantenservice; those three are so simple that the desktop design scales along (measured: no horizontal overflow down to 820px).
  • Measured in the desktop prototype: homepage, catalogue, Downloads and Klantenservice run down to about 820px without horizontal overflow. The product page breaks at 1000px (279px too wide) and the cart at 1000px (222px). That is exactly the matrix.

Check: is the responsive prototype equal to the design?

Comparing by hand is error-prone and slow. That is why a measurement script is included: vergelijk/vergelijk.py opens both prototypes in headless Chrome at 1440 px, records a screenshot and all text lines per screen (position, font size, weight, colour, font family) and reports every difference. A difference of 0 deviating text lines and less than 1% deviating pixels means: equal to the design. On 17 September home is at 0, the product page at 0, Downloads at 0, Productfoto's at 9 lines of 1-2 px and the catalogue at 36 lines of 1-2 px (rounding in the bottom product row).

Two things came out of the design itself in the process: the product card in the catalogue had a different line height on the name than the one on the homepage (PLPD has been aligned with HomeD: line-height:1.35, colour dots 14 px), and the Downloads intro still mentioned forms (now "en de Pricat"). The script also measures at 390 px (against the mobile prototype) and 768 px (against the tablet prototype): python3 vergelijk/vergelijk.py 390 and ... 768. After the corrections of 17 September everything at those widths is within a few pixels; what remains are differences between the artboards themselves, where the responsive prototype follows the desktop choice:

  • the label below the bags category ("Tassen" on mobile and tablet, "Accessoires" on desktop; decision 18 September: Accessoires, as the responsive prototype already did);
  • the mobile product page shows an outlet price for Navy, the desktop does not;
  • Productfoto's on mobile shows six of the nine collections, the responsive prototype all nine;
  • the tablet design has no copyright line in the footer; the responsive prototype does have it;

The label below the bags category became Accessoires on 18 September. The fixed mobile and tablet prototypes are frozen and do not follow these decisions; the responsive prototype does. Tokens

Tokens as a file

The tables below also exist as code in b2b-design/code/, generated with bouw-tokens.py from the same source as this document. So copying by hand is not necessary.

FileWhat is in it
tokens.cssAll tokens as custom properties (--robey-color-gold, --robey-radius-cell, …). Import and use them directly.
tokens.jsonThe same values as data, with the role per token. For a Tailwind theme, a JS constants file or another system.
componenten.cssThe parts where the design is precise and guessing goes wrong: the size cell with all its nine states, the buttons (with the rule that gold belongs only to the cart), labels, prices, order type labels, amounts and the 4:5 tile photo.
voorbeeld.htmlA sheet that uses only those two stylesheets and otherwise not a single colour or size of its own. So what is there is what you get. Open it to check that the import is correct.

The build fails if a colour value does not occur in the artboards, so that the files cannot silently drift out of step with the design.

This is deliberately not the layout of whole pages: those are rebuilt with real data, and the prototype code is throwaway work (inline styles, generated). Tokens and the parts with many states are stable, and that is exactly where things go wrong otherwise.

Availability per size: three states and an upper limit

Decision and advice of 18 September, following the question of what happens when a dealer wants more than there is. Per size there are three states, and they are shown in the cell itself, not in a pop-up:

Stock and preorder

The difference is not now versus later, but from our stock (including what is still coming in) versus specially produced for this customer. So a size that is sold out in stock mode can be ordered and follows later; that is the orange state. In preorder no stock figures are shown.

The toggle is per article; whether an article can have both stock and preorder depends on how seasons are tagged in Shopify (Data questions).

#898989 on white achieves 3.5:1. Recommendation: #898989 only for decorative gray (lines, icons) and for text from 14 px bold. Everything that has to be read at 11–13 px: #5C5C5C (7.0:1). The orange focus ring: a thicker 3 px border in the field itself, or make the field white on focus so the ring falls on white.
